# 已知问题与验证缺口

当前为0.1.3统一源码候选，实际验收见 [ACCEPTANCE.md](ACCEPTANCE.md)。

## 模型读取与工程结论

本机匿名样例已在同一次整阀调用中实读原始 PDF、devdata 和规格书，并完成冻结和报告链。此前云端原件读取失败的根因没有单独证实；不能保证所有远端环境同样可读。读取声明门禁验证结构、覆盖和绑定，仍须核对真实工具轨迹。旧冻结包缺少声明时仅 `legacy_unrecorded` 只读兼容，不补写来源。

软件样例成功不证明真实设备诊断准确或符合投用条件。原始输入、适用阈值、规格、全部曲线和人工反馈仍须按现有流程核验。

## 提取与型号边界

- 已移除从阀型号通用前缀推断执行机构型号，缺失保持缺失。保留的 `-21129` 显示特例仍需现场来源核实。
- 合成序列号含连字符时 PDF 提取截断，虽已通过原件实读识别冲突，通用解析未在本轮扩大修改。
- 已验证的规格标签、单位和带图复核不能覆盖未知模板、复杂表格、中文及低质量扫描；有源值但解析不可靠时继续复核。
- 已复核数值带匹配单位的显示问题已修复；不同单位不自动换算。负号、标点及实际漏字仍保留内容验收约束。

## Docker 与交付环境

本机已有 WPS 实际导出和七页视觉验收通过；这不等于 Docker 内 WPS、许可或另一台机器已验证。默认 Docker 镜像不含 WPS，不能用于正式 PDF 交付。LibreOffice PDF 只用于内检。

Compose/Buildx 官方插件已核对校验值并安装，诊断镜像已构建。宿主机127.0.0.1代理不能直接供桥接容器使用；本机构建使用 host 网络，不把代理端口写入分发配置。Ubuntu 受限用户命名空间需管理员加载诊断专用 AppArmor 规则，不能因此关闭原件隔离。PaddleX 3.3 即使禁用图表也加载 PP-Chart2Table，本版本采用上游已修复的 PaddleOCR/PaddleX 3.5.0；已缓存模型显式传目录，避免启动先检查远端。当前两个 CPU OCR 接口实际识别通过；本机诊断容器隔离仍等待专用 AppArmor 规则加载后的验收。

第一目标为Linux x86_64；第二台干净机器、其他系统、ARM与GPU未验收。接收方自行登录并具备目标模型和系统隔离能力。外部组件授权按各自要求核对。
